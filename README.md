# DocSearch

Ask a question about Python, FastAPI or PostgreSQL and get back the passages from
the official documentation that match it — copied verbatim, ranked by embedding
similarity, and linked to the page each one came from.

**There is no language model in this system.** The only inference is a 22M-parameter
sentence encoder that maps text to a 384-number vector. Nothing is generated,
paraphrased, summarised or answered. A result is a quote and a link, or it is
nothing at all.

---

## How it works

```
INGESTION (local, on demand — never runs in production)
──────────────────────────────────────────────────────
  docs.python.org/3 ──┐
  fastapi.tiangolo.com├──▶ discover pages ──▶ extract sections ──▶ chunk
  postgresql.org/docs ─┘   (site's own         (heading-aware,       (code blocks
                            index/sitemap)     keeps <pre> whole)     never split)
                                                                       │
                                                                       ▼
                                                          embed with MiniLM-L6-v2
                                                                       │
                                                                       ▼
                                                     upsert into Postgres + pgvector

QUERY TIME (Vercel serverless function)
───────────────────────────────────────
  question ▶▶ embed ▶▶ two rankings at once ▶▶ fuse ▶▶ verbatim passages
                 (local)   cosine + BM25        (RRF)      + source URL
```

### Retrieval, in four steps

1. **Embed the question** with the same `Xenova/all-MiniLM-L6-v2` model used at
   ingestion, producing an L2-normalised 384-dimension vector.
2. **Rank every passage twice**, in one statement: by cosine distance to that
   vector, and by Postgres BM25 over the literal words.
3. **Fuse the two rankings** with Reciprocal Rank Fusion. The relevance threshold
   and the manual filter are applied inside the same query, so filtering never
   reduces the candidate pool.
4. **Return the stored text as-is**, with its heading path, section title and
   canonical URL.

### Why two retrievers

A sentence encoder is weak at exactly the queries a documentation index gets
asked. `httpx.AsyncClient` and prose about HTTP clients land close together,
because a 22M-parameter model has no distributional reason to represent the
identifier distinctly. BM25 matches the literal term and recovers those.

They are combined by rank rather than by score: each retriever contributes
`1 / (60 + rank)` and the two are added. A cosine distance and a BM25 score are
not on a comparable scale, and normalising them into one would invent a
relationship that is not there.

Measured on the verification set: asking how to return a file response from a
FastAPI route ranked a status-codes page first and `FileResponse` third. Adding
the lexical retriever puts `FileResponse` first.

### About the scores

Similarity is cosine distance between two embeddings. A high score means the
passage and the question sit close together in embedding space — which reflects
vocabulary and phrasing as much as meaning. **It is a ranking signal, not a
measure of correctness.** The interface says so, and every result links to the
source so you can check it in context.

## Local setup

Requires Node 20+ and a Postgres 16+ database with the `vector` extension
(Neon free tier is the intended target).

```bash
npm install
npm run model:fetch          # ~23 MB of weights into ./models
cp .env.example .env.local   # then fill it in
npm run db:migrate
```

### Environment variables

| Variable | Required | Purpose |
|---|---|---|
| `DATABASE_URL` | yes | **Pooled** connection (`-pooler` host). Used for all query traffic. |
| `DATABASE_URL_UNPOOLED` | yes | **Direct** connection (no `-pooler`). Required for migrations and `CREATE EXTENSION`. |
| `EMBEDDING_MODEL` | no | Defaults to `Xenova/all-MiniLM-L6-v2`. |
| `EMBEDDING_DIM` | no | Defaults to `384`. Must match the column definition. |
| `SEARCH_TOP_K` | no | Default result count (default `8`, capped at 25). |
| `SEARCH_THRESHOLD` | no | Minimum cosine similarity (default `0.38`). |

### Choosing the relevance threshold

The default is calibrated against the indexed corpus rather than guessed, and
the figures below are generated by `npm run db:stats -- --facts`, not typed in.
Across the top 25 candidates for 10 real questions, the **weakest genuine match
scored 0.418**. Across 5 questions with no answer in these manuals, the
**strongest unrelated match scored 0.260**. `0.38` sits in that gap with margin
on both sides.

Raise it if you would rather return nothing than return something loosely
related. Lower it if you are willing to trade precision for recall. Set it to
`0` to disable filtering and rank the whole corpus.

The threshold gates both retrievers. BM25 decides *ranking*; it does not decide
*admission*. Letting term overlap alone admit a passage made "what is the
capital of France" return results, because these manuals do mention France
somewhere.

### Why two connection strings

Neon's pooled endpoint routes through PgBouncer in **transaction mode**, which
cannot service session-level state. `CREATE EXTENSION` and most migration tools
will fail against it — usually in a way that does not mention pooling
(`prepared statement "s0" already exists`, a `search_path` that silently resets,
`SQLSTATE 25006`). Migrations use the direct string; everything else uses the
pooled one.

## Ingestion

```bash
npm run ingest                                  # all three manuals
npm run ingest -- --source fastapi              # one manual
npm run ingest -- --source python --source postgresql
npm run ingest -- --limit 20                    # smoke test on 20 pages
npm run ingest -- --refresh                     # ignore the HTTP cache
npm run ingest -- --target-tokens 400           # larger passages
```

### Design decisions worth knowing

**Sections, not pages.** Each documentation heading becomes one row in
`documents`. A passage can therefore be cited precisely — "Bigger Applications →
Dependencies" — instead of "somewhere on a long page".

**Chunk size is bounded by the encoder, not by taste.** all-MiniLM-L6-v2 has a
256 word-piece position limit, and a longer passage is silently truncated *before*
it is embedded — the tail is stored in the database and can never be matched by
any query. The chunker therefore **measures real tokenisation** rather than
estimating it from character counts, and divides anything that overruns.

Estimating was tried twice and was wrong in both directions. Characters per
word-piece ranges from 5.0 in ordinary prose to 1.33 in PostgreSQL's operator
tables, where each line is a few symbols. A constant sized for the densest
content left 32 chunks per 60 pages truncated; a constant sized for prose
fragmented the FastAPI corpus from 2,803 passages into 11,702 by cutting good
prose into unreadable fragments. Neither failure announced itself.

Prose is split with LangChain's `RecursiveCharacterTextSplitter`. **Code blocks
are split only at line boundaries**, and only when they overrun the limit — a
newline is a syntactic boundary in every language in the corpus, so no statement
is ever cut in half. Content that is stored but can never be matched is dropped
at extraction instead: inline base64 blobs, contributor mention lists, and
Mermaid diagrams' inline HTML markup.

`tests/chunk-model-fit.test.ts` measures all of this against the real tokenizer,
so the limit cannot silently regress.

**Discovery caps are never applied silently.** Each source has a `maxPages`
limit, and if discovery finds more pages than the limit allows, ingestion warns
loudly. This matters: PostgreSQL's `sql-*.html` reference pages sort last
alphabetically, so a cap set too low drops the entire SQL Commands reference
while looking like a corpus that simply never covered the topic.

**Re-running is safe and cheap.** Documents are keyed by
`(source, url, anchor)` and chunks by `(document_id, ordinal)`, so ingestion
upserts in place. Each chunk carries a content hash; only chunks whose hash
changed are re-embedded. An incremental run costs almost nothing.

**Sections removed upstream are pruned.** On a complete pass, documents that no
longer appear are deleted. Pruning keys on `(url, anchor)`, not on the URL alone:
a section can survive upstream while ceasing to produce any passages, and a
URL-only prune would keep those stale rows forever — never refreshed, never
removed, and still returned by queries. This is skipped when `--limit` is set,
so a smoke test cannot wipe the index.

**Polite crawling.** Requests are serialised per host with a fixed delay, sent
under a descriptive User-Agent with a contact URL, and checked against each
host's `robots.txt`. Responses are cached in `.cache/` (gitignored) so re-runs
do not re-fetch unchanged pages. Discovery uses the site's own
`contents.html` / `sitemap.xml` where one exists rather than blind crawling.

**Writes are batched.** Neon is geographically distant, so a round trip costs a
few hundred milliseconds. Documents and chunks are written with set-based
statements in batches of 100, which turns a multi-minute ingest into a
one-minute one.

## Query performance

Measured against the deployed function (Vercel Hobby, `iad1`, Neon in
`us-east-2`):

| | |
|---|---|
| Cold start, including loading the model | ~2.5 s |
| Warm query | ~350–650 ms |
| Empty result set | ~0.5–0.9 s |

The cold start is the embedding model being read from the function bundle. It
is paid once per instance and then amortised across warm requests.

## What LangChain is used for, and what it isn't

This project uses LangChain, but deliberately not the `langchain` umbrella
package. That package pulls in **LangGraph** — a stateful agent and workflow
orchestration engine — which has nothing to contribute to a retrieval-only
index. Depending on `@langchain/textsplitters` and `@langchain/core` directly
gets the parts that help without the agent framework:

```
langchain (umbrella)   -> langgraph, langsmith, js-tiktoken, zod, ...   56 MB
@langchain/textsplitters
  + @langchain/core    -> langsmith, js-tiktoken, zod                    44 MB
                        (no langgraph)
```

**Used:** `RecursiveCharacterTextSplitter` replaces a hand-rolled regex that
divided prose on sentence boundaries. It walks a hierarchy of separators —
paragraph, line, sentence, clause, word — and only hard-cuts once every
separator is exhausted, which is more robust and better tested than what it
replaced. Chunks are emitted as LangChain `Document` objects (`pageContent` +
`metadata`), so the index is interchangeable with any LangChain vector store or
retriever if that is ever wanted.

**Not used, deliberately:**

- **The umbrella `langchain` package**, because it drags in LangGraph.
- **Any vector store wrapper.** `PGVector` would hide the SQL that pushes the
  relevance threshold and source filter *into* the query. For a tool whose
  entire premise is showing exactly what was retrieved and why, that SQL is
  worth reading. BM25 is queried the same way, in the same statement.
- **Any LLM.** LangChain does not force one in the retrieval path, and none is
  used here. `HuggingFaceTransformersEmbeddings` would only wrap the same
  transformers.js call the code already makes.

`LANGSMITH_TRACING` is not set and LangSmith tracing is never enabled, so the
`langsmith` package that ships as a transitive dependency stays inert.

### It costs the deployment nothing

The embedding runtime and LangChain are used in different halves of the system.
The search function embeds a query and runs SQL; it never chunks a document.
Chunking runs only in the local ingestion CLI, which is never bundled. Measured
after adding LangChain, the traced function payload is **unchanged at 88.6 MB**,
and `node_modules/@langchain/**` does not appear in it at all.

## Deployment

Deployed to Vercel with the Vercel CLI.

```bash
vercel --prod
```

Set `DATABASE_URL` in the Vercel project's environment variables — either in the
dashboard, or with `vercel env add DATABASE_URL production`, which prompts for
the value in your terminal so it never passes through a log or a chat.

`next.config.ts` sets `outputFileTracingIncludes` so the model weights and the
ONNX runtime are traced into the serverless function. Two things there are easy
to get wrong:

- The native library is loaded through a *dynamic* `require` on
  `process.platform` / `process.arch`, so the tracer cannot follow it. Only the
  Linux x64 build is included by hand; the darwin, win32 and arm64 builds are
  ~240 MB of dead weight that would breach the bundle limit.
- `@huggingface/transformers` is listed in `serverExternalPackages`, which also
  stops the tracer from following into `onnxruntime-node` — so that package has
  to be included explicitly as well, not just its binaries.

The embedding stack is imported lazily inside `search()` so that rendering the
landing page never loads onnxruntime or the model.

Only the pooled `DATABASE_URL` is needed in production. Ingestion and migrations
are local operations and never run on Vercel.

### Free-tier limits — read this before relying on the deployment

Neither provider offers an availability guarantee, and both can change their
terms without notice.

**Vercel Hobby**
- Personal, non-commercial use only. Commercial use requires a paid plan.
- 2 GB memory / 1 vCPU per function, 250 MB uncompressed bundle.
- 4 active CPU-hours per month. This project uses roughly 0.2 s of CPU per
  query, which puts the ceiling around 70,000 queries a month — but the model
  has to be loaded on each cold start, and that load counts too.
- 100 GB bandwidth/month, 1M function invocations/month.
- No GPU. The model is small enough that CPU inference is the right choice.

**Neon Free**
- 0.5 GB storage, 100 compute-hours/month, autoscaling to 2 CU.
- **Scale to zero after 5 minutes idle.** The first query after an idle period
  pays a cold start of a few hundred milliseconds on top of the model load.
  This is the single most user-visible rough edge of the deployment.
- The indexed corpus currently occupies about **161 MB**, roughly a third of
  the storage allowance. Room for several times the current documentation
  before it becomes a constraint.

**Function size**

The deployed function traces to about **89 MB** uncompressed, against Vercel's
250 MB limit. Almost all of it is the ONNX runtime for Linux x64 (44 MB) and
the int8 model (22 MB).

**If the demo gets real traffic**, the first thing to break will be Vercel's CPU
hour budget, then Neon's compute hours. Both are fixable by moving ingestion to
a scheduled job and caching queries, not by scaling the model.
